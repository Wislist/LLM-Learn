Prompt 工程精读笔记

Anthropic Guide + DeepSeek System Prompt 拆解 — 2026-07-02

这些是 Week 2 的必读材料。你不需要背下来，但要知道"写了什么、为什么这么写"。 你写 mini-opencode 的 system prompt 时，这里的技术全部会用到。

1 Anthropic Prompt Engineering Guide

Anthropic 把他们的 prompt 工程经验总结成了六条策略。 这里列的是对 Agent 开发者最有用的部分。

1. Be clear and direct

原则：告诉模型你要什么，而不是不要什么。"写一个 Go 函数，反转字符串" 比"不要用 Python，不输出多余内容"更有效。

用在 Agent 上：

// ❌ 差
"不要编造文件内容，不要一次改太多文件"

// ✅ 好
"在修改文件之前，先用 read_file 工具读取文件内容。
修改完成后，用 write_file 写入。每次只修改一个文件。"

2. Use examples (few-shot)

原则：给 2-3 个例子比写 10 行规则更有效。模型天然擅长"照猫画虎"。

用在 Agent 上：在 system prompt 里放几个"正确"的 tool call 样例：

// system prompt 里的 few-shot
"当你需要读取文件时，这样调用：
<tool_call>
{"name": "read_file", "arguments": {"path": "main.go"}}
</tool_call>

当你需要搜索代码时，这样调用：
<tool_call>
{"name": "search_code", "arguments": {"query": "func ReadFile"}}
</tool_call>"

3. Give the model room to think

原则：如果任务复杂，让模型先输出思考过程再输出答案，"Let's think step by step"。 只给一个简单问题可能得到错误答案，加一句思考邀请大幅提升准确率。

用在 Agent 上：Agent 的 system prompt 里加 "在调用工具之前，先说出你的计划"。

4. Use XML tags

原则：用 <标签>...</标签> 分隔 prompt 的不同部分， 比 Markdown 标题或空行更可靠。模型在训练数据中见过大量 XML，理解更准确。 

<task>
  帮我重构 main.go 中的 ReadFile 函数，使其支持大文件分片读取。
</task>

<context>
  项目是一个 CLI 工具，使用 cobra 框架。
</context>

<constraints>
  - 保持向后兼容
  - 不要引入新依赖
</constraints>

用在 Agent 上：system prompt 里用 <tools>、<rules>、<examples> 分组，模型能准确区分"能力描述"和"行为约束"。

5. Let the model complete

原则：模型在生成过程中自己纠正错误。不要过早打断。 比如问完问题后，在 prompt 末尾加一个不完整的句子让模型续写，比等模型完全自由发挥更可控。

用在 Agent 上：Agent 的 prompt 末尾可以接 "让我们一步步来：首先，" 引导模型启动思考链。

6. Chain of Thought

原则：明确要求模型先推理再回答。对数学、逻辑、多步骤规划类任务效果显著。 对简单的工具调用可能反而浪费 token，所以按需使用。

用在 Agent 上：如果任务跨多个文件（如"重构整个模块"），让模型先输出计划再动手。简单的"读文件"就免了。

2 DeepSeek System Prompt 拆解

DeepSeek 开源了他们 V3 模型的 system prompt（GitHub: deepseek-ai/DeepSeek-V3）。 以下是它对 Agent 开发者最有参考价值的部分。

整体结构

DeepSeek 的 system prompt 大约占 500-800 tokens，分为几块：

段落内容作用
身份定义"You are DeepSeek, a helpful assistant..."设定性格和知识边界
工具描述按编号列出所有可用工具，每个带名称、参数、输出格式告诉模型"你有什么工具"
调用规则"每次只调一个工具"、"不要编造工具输出"行为约束
输出格式指定返回格式、思考过程要不要输出、如何引用文件保证解析一致性
示例2-3 个完整"用户 → 思考 → 调用 → 工具结果 → 回复"的样例few-shot

关键设计选择

1. 编号工具

DeepSeek 的工具描述使用编号而非嵌套 JSON：

工具列表：
1. read_file
   描述：读取文件内容
   参数：path (string, 必填) - 文件路径
2. write_file
   描述：写入文件
   参数：path (string, 必填) - 文件路径
          content (string, 必填) - 文件内容

这样在 context 窗口压缩时，编号格式比完整 JSON Schema 更省 token。但你的 Agent 用的是 API 层的 tools 参数（JSON Schema），格式由 Provider 决定，你不需要自己写这种编号格式。

2. ReAct 风格的思考链

DeepSeek 的 system prompt 明确引导模型先输出思考再行动：

"在每次调用工具之前，简要说明你的推理过程。
这有助于确保你正确理解用户需求。"

3. 错误预防条款

这是 system prompt 里最容易被忽略但实际最重要的部分：

"- 不要假设工具的输出。只使用工具实际返回的数据。
- 如果工具调用失败，不要重试超过 3 次。
- 如果读不到文件，告诉用户文件不存在，不要用类似文件名替代。"

对 Agent 开发者的启发

从 DeepSeek 的 system prompt 里学到的最重要的三件事：

1. 错误处理比正常流程更需要写清楚
模型天然倾向于"假装成功"（幻觉）。你的 system prompt 必须明确写出"XX 情况下怎么办"。

2. 输出格式约束必须可解析
不要只靠"请用 JSON 格式回答"。加 tool_calls 参数或加 stop words，让格式出错时你的代码也能恢复。

3. 示例的格式要跟实际输出一致
Few-shot 里给什么格式，模型就学着输出什么格式。所以例子里的 tool call JSON 字段名和真正的 tools 参数必须严格一致。

3 总结：Agent 开发者该带走什么

写 system prompt 的检查清单：

  1. 身份清晰（一句话说明"你是谁"）
  2. 能力边界（"你能做什么、不能做什么"）
  3. 工具描述（每个工具的 name + desc + params 不能少）
  4. 错误处理（"读不到文件怎么办"、"工具报错怎么办"）
  5. 输出格式（"每条回复应该包含什么"）
  6. 2-3 个完整示例（few-shot）
  7. 用 XML 或编号分组，不要一大段文字
