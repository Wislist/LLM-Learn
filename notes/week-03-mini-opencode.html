2. 文件详解

config.go

19 行
  • 集中所有可调参数：API key、模型名、最大轮数、历史长度上限
  • 学什么：参数集中在一个 struct 里不是过度设计。当你想加 temperature、自定义 system prompt 时只需要改这一个文件

tools.go

154 行 — 最大的文件
  • 定义 Tool 接口：Name() / Description() / Schema() / Execute()
  • 为什么用接口：每个工具是一组关联的 name + desc + schema + execute。ToolRegistry 不需要知道每个工具内部怎么实现，只要它能回答"你叫什么、你有什么参数、你执行"
  • 为什么 Schema 和 Execute 分开：Schema 发给 LLM 做工具选择，Execute 发给 OS 做真正干活。两个调用方不需要彼此知道细节
  • ToolRegistry 维护两个数据结构：map[name]Tool 用来 O(1) 派发，order []string 用来保持注册顺序

bash.go

69 行
  • 封装 os/exec 调用，三层安全：30s 超时、输出截断 4KB、工作目录锁定项目根
  • Exit code 单独返回，模型能区分"命令成功但输出为空"和"命令失败"

history.go

51 行
  • 封装消息列表，对外只暴露 Add() 和 Messages()
  • 截断保证偶数条：tool call 消息成对出现（assistant tool_calls + tool result），裁奇数条会拆散配对
  • Messages() 每次返回新 slice，避免并发修改

agent.go

122 行 — 核心
  • Agent.Run() 就是"Agent Loop"：发送 → 解析 → 检查 tool_calls → 执行 → 拼回 → 循环
  • 关键设计：System prompt 每次 Run() 时动态生成（prompt + tool list）。如果运行时注册/卸载工具，system prompt 自动反映当前工具集
  • output io.Writer 字段：测试时换成 bytes.Buffer 就能抓取所有输出

main.go

63 行
  • 用 switch 做命令解析：/help /clear /tools exit
  • /clear 不重置 system prompt——"你是谁、你有什么工具"始终保留
  • bufio.Scanner 而非 fmt.Scanln：正确处理空行、中文、长输入

5. 踩过的四个坑

1. 流式 tool_calls 逐字符推送

streamChoice.Delta.ToolCalls 用了完整的 ToolCall 类型，但流式下每个 chunk 只是增量。修复：换成 toolCallDelta（所有字段用 pointer），在 tcAccumulator 里按 index 归并。

2. finish() 重复发文本 → 无限循环

tcAccumulator.finish() 把已发出的文本又发了一次，response 在对话历史里成双份。LLM 看到自己说了两遍就重复。修复：finish() 只发 tool call + done。

3. tool_call_id 缺失 → 400 错误

tool 结果拼回对话时忘了 tool_call_id。修复：Message 加 ToolCallID 字段。

4. assistant tool_calls 消息未保留

只追了 user + tool 结果，忘了 assistant 的 tool_calls。LLM 看不到谁发起的调用。修复：追 tool 结果前先追 assistant 消息（含 ToolCalls）。
