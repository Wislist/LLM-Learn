1 全景：Agent 运行时在跑什么

所有类 opencode 的 Agent 在工作时，脑子里都跑着同一个循环。 把这个刻进脑子里，它是你写框架的地基。

重点：步骤 2（构建 Prompt）和步骤 4（解析响应）是你 作为 Agent 框架开发者需要写最多代码的地方。LLM 调用本身就是一个 HTTP 请求。

2 Prompt：你发给 LLM 的那包话

结构

一个 HTTP 请求到 LLM API 的 body 长这样。这是 OpenAI / DeepSeek 兼容格式： 

{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是一个编程助手..."},
    {"role": "user",   "content": "帮我在 main.go 加个 ReadFile 函数"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "read_file",
        "description": "读取指定文件的内容",
        "parameters": {
          "type": "object",
          "properties": {
            "path": {"type": "string"}
          }
        }
      }
    }
  ]
}
部分作用
messages对话本身。System 是"你是什么"，User 是"用户说了什么"
tools告诉 LLM："你可以调这些函数"

System Prompt 是关键

System Prompt 是一个 Agent 的人格 + 行为规范。opencode 的 system prompt 会告诉模型：

  • 你的身份（"你是一个软件工程助手"）
  • 你拥有的能力（"你可以读写文件、执行命令"）
  • 行为规范（"每次只改一个文件 / 读完文件后再决定 / 不要编造不存在的内容"）
  • 输出格式（"用 markdown 代码块输出 diff"）

写好 system prompt 是 Agent 开发中最关键也最容易被低估的一步。 一条写得好的 system prompt 可以让模型在行为上"看起来像是专门训练的"。

3 Tool：Agent 跟世界交互的接口

什么是 Tool

LLM 本身只有"生成文本"的能力。它不能读文件、执行命令、搜索网络。 所以 Agent 需要给它"安装"工具。

每个工具的定义包含三部分：

字段作用例子
name工具名read_file
descriptionLLM 靠它决定"要不要用""读取文件内容，不超过 100KB"
parameters参数 schema{"path": "string"}

LLM 怎么"调用"工具

当 LLM 决定要用工具时，它输出 tool_calls 结构：

{
  "content": null,
  "tool_calls": [
    {
      "id": "call_xxx",
      "type": "function",
      "function": {
        "name": "read_file",
        "arguments": "{\"path\": \"main.go\"}"
      }
    }
  ]
}

你的框架要做的三件事：

  1. 解析 tool_calls 结构
  2. 派发到对应的 Go 函数执行
  3. 将结果作为 tool role 消息拼回对话

Hermes 有什么不同

你计划里提到了 Hermes。Hermes 不用 OpenAI 的 JSON 格式，它用 XML 风格 token：

<tool_call>
{"name": "read_file", "arguments": {"path": "main.go"}}
</tool_call>

解析时需要匹配 <tool_call> 标签，再用 encoding/json 二次解析。 这种设计的优点：Hermes 在训练时内置了这个格式，出错的概率比用 prompt hack 的方式低很多。

4 Skill：Tools 的组织包装层

Skill 本质上是什么

一个 Skill = 一组相关的 Tools + 一段额外的 System Prompt。

type Skill struct {
    Name         string    // "code_editor"
    Description  string    // "提供代码编辑能力"
    Tools        []Tool     // read_file, write_file, search_code
    Instructions string    // "使用代码编辑 skill 时，先读文件再修改"
}

为什么需要 Skill 这一层

如果只有 Tool，所有工具平铺一长串。模型要从 30 个工具里选出对的，负担很大：

  • 逻辑分组：文件工具归 "code_editor"，搜索工具归 "knowledge_search"
  • 条件加载：做纯代码修改时不需要加载网络搜索工具，减少 token 消耗
  • 上下文注入：每个 skill 带自己的指令，精确控制"用什么姿势用这些工具"

Plugin/MCP 的思路是："我的 Agent 在启动时还不知道自己有什么能力，运行时才加载"。 这也是 opencode 的设计——它有一个 plugin 机制，启动时扫描文件系统，找到 plugins 后加载它们暴露的 tools。

5 完整的 Agent 运行流程

你用 opencode 说"帮我改 main.go 的 ReadFile"时，背后发生的事：

sequenceDiagram participant User as 用户 participant Agent as Agent 框架 participant LLM as LLM participant FS as 文件系统 User->>Agent: "帮我改 main.go 的 ReadFile" Agent->>Agent: 构建 Prompt (System + 历史 + tools + user) Agent->>LLM: 发送 API 请求 LLM->>Agent: tool_call: read_file("main.go") Agent->>FS: 读取文件内容 FS->>Agent: 返回 main.go 代码 Agent->>Agent: 把文件内容以 tool role 拼回对话 Agent->>LLM: 再次发送（含文件内容） LLM->>Agent: tool_call: write_file("main.go", 修改后代码) Agent->>FS: 写入修改 FS->>Agent: 写入成功 Agent->>Agent: 把结果拼回对话 Agent->>LLM: 再次发送 LLM->>Agent: 文字回复："已修改 ReadFile 函数..." Agent->>User: 展示修改结果

这就是一个 Agent 的全部。 没什么魔法。你一步步跟踪这个流程，就能写出自己的实现。

6 你现在该做什么

基于上面这些理解，Week 1 的实际路线：

第 1 步：用手摸 API — 30 分钟

用 curl 调一次 DeepSeek API，亲眼看看 SSE 流式数据长什么样：

# 用 DeepSeek API 发一条最原始的请求
curl https://api.deepseek.com/chat/completions \
  -H "Authorization: Bearer $DEEPSEEK_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek-chat",
    "messages": [
      {"role": "system", "content": "你是一个编程助手"},
      {"role": "user", "content": "用 Go 写一个 Hello World"}
    ],
    "stream": true
  }'

你的 Agent 框架最复杂的部分就是解析这种流式输出。先看看原始数据长什么样。

第 2 步：用手摸 Tool Calling — 30 分钟

在 curl 参数里加上 tools 字段，观察 LLM 返回 tool_calls 时的原始输出结构。

第 3 步：手写极简 Agent Loop — 2 小时

不借助任何框架，用 Go 的 net/http 写出这个循环：

发送 API 请求 → 解析响应 → 检查是否 tool_call
                    → 如果是：执行工具 → 结果拼回 → 再发送
                    → 如果否：展示回复给用户

5 个 Go 文件就能跑通。这叫你的 mini-opencode v0.1。

第 4 步：拆 opencode 的插件机制 — 复盘

你已经有 opencode 装在 /Users/wislist/.config/opencode/ 了。 去看看它的 plugin 目录，JS 文件是怎么写工具的。理解别人是怎么搞的，然后决定你的 Go 版要支持 JS plugin 还是走 MCP。

Agent = Prompt 工程（怎么跟 LLM 说话）
            + Tool 调度（怎么让 LLM 操控真实世界）
            + 一个跑在中间控制流量的循环。

写一个自己的 opencode，就是在 Go 里实现这三个东西，并且让它们配合流畅。
